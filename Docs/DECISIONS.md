# Sayt — 설계 결정 기록

## 이 문서의 목적과 범위

**코드와 커밋 이력을 읽으면 알 수 있는 것은 적지 않는다.** 무엇을 만들었는지,
어떤 클래스가 있고 어떻게 동작하는지는 repo를 보면 나온다.

여기 남기는 것은 **코드에 흔적이 남지 않는 것**이다.

- 왜 그 선택을 했는가
- 무엇을 고려했다가 버렸는가, 그 이유는
- 무엇이 측정으로 확인되거나 반증되었는가
- 어떤 판단을 의도적으로 미뤘는가

용도는 Phase 12의 포트폴리오 README 작성과 모의 면접 준비다.
"왜 이렇게 만들었나"에 답할 근거가 대화 기록에만 남아 있으면 그때 다시 발굴해야 한다.

**분량 기준은 없다.** 결정의 중요도에 따라 정한다.

### 기록 시점

- Stage/Phase 종료 시 그 구간의 결정을 기록
- Phase 0~7은 소급 작성하지 않는다. 해당 개념이 남은 로드맵에서 재등장할 때
  재학습과 함께 채운다 (Stage 4 → 풀링·GMS, Phase 10 → GAS 코어,
  Phase 11 → DataTable·전투). 재등장하지 않는 인벤토리(Phase 5)와
  EUW(Phase 7)는 Phase 12 모의 면접 준비 때 작성

## Stage 2 — 세그먼트 체력 표시 / 몬스터 월드 패널

### 내장 `UWidgetComponent` 대신 커스텀 패널을 만든 이유

액터 머리 위 UI는 엔진 내장 기능으로 가능하다. `UWidgetComponent`를 붙이고
UMG 위젯을 지정하면 되고, 모드가 두 가지다. World Space는 위젯을 3D 공간의
판에 그려 벽에 가리고 원근을 따르며, Screen Space는 액터 위치를 화면에 투영해
뷰포트에 그린다 — 후자는 이 패널과 발상이 같다.

**소규모라면 내장이 합리적이다.** 몹이 몇 마리고 목표가 "동작하는 체력바"뿐이면
코드량이 압도적으로 적다. 그럼에도 커스텀을 택한 근거는 셋이다.

1. **중앙 통제가 필요한 기능들.** 위젯 풀, 거리 기반 컬링, 겹칠 때 정렬 순서,
   화면 밖 대상의 가장자리 클램핑 — 전부 "전체를 아는 한 곳"이 있어야 성립한다.
   액터마다 독립적으로 붙는 컴포넌트 구조로는 어렵다.
2. **Lyra가 같은 이유로 같은 선택을 했다.** 내장 컴포넌트가 있는데도 별도
   인디케이터 시스템(`IndicatorManagerComponent`/`SActorCanvas`)을 둔다.
3. **Phase 8의 목적이 Slate 심화.** 내장으로 우회하면 학습 단원 자체가 사라진다.

이 비교 자체가 포트폴리오 자산이다 — "내장을 몰라서 만든 게 아니라 한계를 알고
선택했다"는 서사. 실측 비교(두 모드를 실제로 붙여 캡처)는 Phase 11로 이연.

### Widget Role = Panel

Stage 1의 `SSaytHealthBar`는 Leaf(자식 없음, 직접 그리기), 파트 A의
`SSaytHealthDisplay`는 Compound(고정 구조 조립). 이 패널이 Panel인 이유는
**자식 수가 동적**이고(몹이 늘고 줆), **"자식을 어디에 어떤 크기로 놓을지"라는
배치 규칙 자체가 존재 이유**이기 때문이다.

파생되는 성질: 자식은 자기 위치를 모른다. 위치 데이터는 슬롯(부모 소유)에 있고
매 프레임 부모가 계산해 자식에게 부여한다.

### 등록 채널 — 방송(GMS)이 아니라 목록 소유 + 델리게이트

Phase 6에서 만든 Gameplay Message Subsystem을 쓰지 않았다.

판별 기준은 **전달하려는 것이 "사건"인가 "상태"인가**이다. 데미지가 들어왔다는
것은 사건이라 순간을 알리면 끝이지만, "현재 표시 중인 대상 목록"은 상태다.
늦게 참여한 구독자(HUD 재생성, 플레이어 리스폰)가 그 전에 등록된 것을 알아야
하는데 방송은 지나간 것을 다시 들려주지 않는다.

그래서 목록을 소유한 주체 + 변경 알림 델리게이트 + 목록 조회 함수 조합.
HUD는 구독 직후 현재 목록을 순회해 따라잡는다. 이 처리가 없으면 리스폰 때마다
살아 있는 몹의 바가 통째로 사라진다.

### 매니저를 Subsystem이 아니라 PlayerController 컴포넌트로

화면 표시 대상은 **로컬 플레이어마다 다르다.** 분할 화면에서는 플레이어별로
목록이 달라야 하고, Phase 10의 네트워크 환경에서는 각 클라이언트가 자기 화면만
관리한다. 월드에 하나뿐인 Subsystem으로는 표현이 안 된다.

부수 이점으로 생명주기가 컨트롤러와 함께 끝나 정리가 저절로 맞는다.

### 대상 참조는 약참조 + 파괴 이벤트 자동 해제

강참조로 들면 몹이 파괴돼도 매니저가 붙잡아 GC가 회수하지 못하고, 원시 포인터로
들면 무효 여부를 알 방법이 없다. 관찰하는 참조는 약참조다.

더 중요한 것은 **해제를 호출부의 기억력에 맡기지 않은 것**이다. 몹을 없애는
경로는 사망·디스폰·레벨 정리·레벨 스트리밍 아웃 등 여럿이고, Phase 11에서
사망 로직이 추가되면 더 늘어난다. 각 경로가 등록 해제를 기억해야 하는 구조는
한 곳만 놓쳐도 누수가 난다. 액터의 `OnDestroyed`에 묶어 전 경로를 한 번에 덮었다.

### 표본 추출과 배치 계산의 분리

초기 구현은 화면 투영을 배치 콜백(`OnArrangeChildren`) 안에서 직접 수행했다.
동작은 했지만 **"캐싱이 꺼져 있다"는 환경 설정에 정확성을 의존**하고 있었다.
캐싱이 켜진 환경에서는 이 패널이 아무 변화 신호도 보내지 않으므로 배치가
재계산되지 않고 화면이 굳는다.

교정: 카메라 표본 추출을 ActiveTimer로 분리해 결과를 슬롯에 캐시하고, 배치
콜백은 캐시만 읽는 순수 계산으로 남겼다. **프레임워크가 부르는 계산 콜백은
프레임워크가 추적할 수 있는 입력만 참조해야 한다** — 그래야 "입력이 안 변했으면
결과 재사용"이라는 캐싱이 성립한다. 콜백 시그니처가 `const`인 것이 이 계약을
문법으로 강제한다.

이 원칙은 Slate 밖에서도 통한다. 메모이제이션·리액티브 갱신을 쓰는 모든 체계의
공통 전제다.

### 투영 재료는 프레임당 1회만 조립

`APlayerController::ProjectWorldLocationToScreen`을 대상마다 부르면 내부에서
뷰 정보를 매번 다시 조립한다. `ULocalPlayer::GetProjectionData`로 뷰·투영 행렬을
프레임당 한 번 뽑고 루프에서는 행렬 곱만 반복하는 형태로 바꿨다
(Lyra `SActorCanvas`와 같은 구조).

**이득이 대상 수에 비례**하므로 몹 3마리 테스트에서는 차이가 안 보인다. 지금
눈에 안 보이는 차이를 구조로 미리 잡아 둔 결정이며, Phase 9에서 몹 수를 늘려가며
측정할 소재다.

### 거리 스케일을 `FSlateLayoutTransform`에 실은 이유

위젯을 작게 만드는 방법은 배치 단계에서 줄이는 것과 그릴 때만 변환을 곱하는
것(`FSlateRenderTransform`) 두 가지다. 후자는 레이아웃을 흔들지 않으므로 형제가
밀리지 않는다는 장점이 있다.

그럼에도 배치 변환에 배율을 실은 이유는 **상태가 나뉘지 않기 때문**이다.
`FSlateRenderTransform`을 쓰면 위치는 배치가, 크기는 위젯의 별도 속성이 관리하게
되어 동기화 책임이 생긴다. 지금 방식은 위치와 배율이 모두 슬롯 캐시에 있고 한
곳에서 함께 적용되어 어긋날 여지가 없다. 비용 면에서도 어차피 매 프레임 도는
배치 계산에 곱셈 하나를 얹는 것이라 사실상 0이다.

**함정 기록**: 정렬 계산에는 원래 크기가 아니라 배율이 적용된 크기를 써야 한다.
원래 크기를 쓰면 배율 1일 때만 정확하고 멀어질수록 대상에서 왼쪽 위로 벗어난다.
가까이서 테스트하면 절대 보이지 않는 종류의 오차다.

### 위젯 풀을 자체 구현한 이유

엔진의 위젯 풀링 도구는 UMG(`UUserWidget`) 층에만 있다 — `FUserWidgetPool`,
CommonUI의 `ICommonPoolableWidgetInterface`. raw Slate 경로에는 대응물이 없다.

이건 단순한 부재가 아니라 **성능 핵심부를 Slate로 내린 대가**다. Epic이 풀링을
UMG 층에서 제공한다는 것은 그 층에서 하라는 판단이고, 더 낮은 층을 선택한
이상 그 층의 편의 기능은 스스로 갖춰야 한다.

재사용 시 상태 초기화는 별도 함수를 만들지 않았다. 파트 A의 `BindToASC`가
구독 등록과 현재값 조회를 함께 하므로 새 대상에 붙는 순간 표시가 전부 갱신된다.
**단, ASC에서 파생되지 않는 상태(진행 중인 애니메이션, 이름·레벨 같은 비체력
정보, 생성 시점에 고정되는 스타일)가 생기면 이 전제가 깨지고 명시적 초기화가
필요해진다.** 현재 몹 프리셋은 세그먼트 1이라 트레이가 없고 고스트도 꺼져 있어
안전하다.

보관 상한(16)을 둔 이유는 풀링과 상한이 서로 반대 방향으로 당기기 때문이다.
풀링은 순환 비용을 줄이고 상한은 보유량을 줄인다. 상한이 없으면 대규모 전투에서
부풀어 오른 최고점이 세션 내내 영구 점유량이 된다.

### 비주얼 폴리시와 측정을 이연한 결정

ROADMAP의 전 Stage 공통 체크리스트 4번(비주얼 폴리시 필수)과 5번(측정 증거)에
어긋나는 **의도된 예외**다.

사유: 몹 하나를 세워 두고 정한 룩과 수치(배경/채움 대비, 기준점 높이, 거리
곡선)는 여러 마리가 AI로 움직이는 화면에서 대부분 다시 바뀐다. 마찬가지로
위젯 풀의 비용 차이와 `UWidgetComponent` 비교도 개체 수가 적으면 유의미한
수치가 나오지 않는다.

이연 대상과 시점은 ROADMAP의 Phase 9·11 항목 참조.

### 실측으로 확인/반증된 것

코드에 남지 않는 정보이므로 여기 기록한다. 모두 이 프로젝트에서 직접 측정했다.

- **뷰포트에 직접 부착한 위젯은 `Slate.EnableGlobalInvalidation`을 켜도 캐싱
  이득을 받지 못한다.** 화면이 완전히 정지한 상태에서도 Prepass/Arrange/Paint
  카운터가 매 프레임 증가(약 120fps 환경에서 초당 120회). 상주 ActiveTimer를
  내려도 동일했으므로 타이머는 원인이 아니다.
- **`SInvalidationPanel`로 감싸면 무효화 신고가 실효를 갖는다.** 감싼 상태에서
  `Invalidate` 호출을 억제하자 카메라를 움직여도 바가 화면에 얼어붙었다.
  즉 `Invalidate`는 명령이 아니라 **신호**이고, 듣는 주체가 있을 때만 의미를 갖는다.
- **초기에 코드 주석으로 단정했던 "정지 화면 = 캐싱으로 완전 휴면"은 거짓이었다.**
  측정 없이 쓴 주장이었고 실측으로 반증되어 주석을 수정했다. 무효화 신고를
  유지하는 근거는 (1) 캐싱이 적용되는 환경에서의 정확성 보장 (2) 비용이 0에
  가깝다는 것이며, 실효 여부는 Phase 9에서 패키징 빌드로 재측정한다.
- **Arrange는 독립된 전체 순회 패스가 아니다.** Paint가 하향식으로 내려가며
  각 위젯이 그리기 직전에 자식 기하를 계산하고, 그 결과는 프레임 끝에 폐기된다.
  "위젯의 현재 화면 위치"라는 영속 데이터는 시스템 어디에도 저장되지 않는다.
